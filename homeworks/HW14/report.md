# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

## 1. Кратко: что сделано

- **База знаний:** 20 справочных FAQ-статей на тему машинного обучения и Python, сгенерированных ИИ, встроенных непосредственно в ноутбук как Python-строки. Выбрана, чтобы база была полностью воспроизводима без внешних файлов и датасетов, при этом содержала достаточно содержательные тексты для осмысленного retrieval.

- **Чанкинг:** символьное разбиение с перекрытием (`chunk_size=300`, `overlap=50`). Граница разбиения выравнивается по ближайшему пробелу, чтобы не разрывать слова. Из 20 документов получилось 65 чанков.

- **Embedding-модель:** `sentence-transformers/all-MiniLM-L6-v2` — плотные 384-мерные нормализованные векторы. Индекс: `faiss.IndexFlatIP` — косинусное сходство через скалярное произведение нормализованных векторов.

- **Оценка retrieval:** 10 контрольных запросов с известными релевантными документами; метрики: `hit@3`, `recall@3`, `MRR@3`. Retrieval показал высокое качество: семантические эмбеддинги хорошо захватывают смысл запроса.

- **Обновление базы знаний:** добавлены 3 новых документа (LSTM, t-SNE, SVM). Переиндексация показала, что после обновления запросы по новым темам начинают корректно находить нужные документы.

- **Mini-RAG:** extractive-шаблонный конвейер - top-3 чанка -> контекст -> ответ по шаблону с указанием источников. Работает без внешнего LLM-API, полностью воспроизводимо.

## 3. База знаний и подготовка документов

- **Предметная область:** машинное обучение и Python (FAQ-формат)
- **Источник документов:** сгенерированны ИИ, встроены в ноутбук
- **Число исходных документов:** 20 (базовая версия) + 3 новых после обновления = 23
- **Число чанков после разбиения:** 65
- **Способ чанкинга:** символьное разбиение с перекрытием, выравнивание по ближайшему пробелу
- **Основные параметры:** `chunk_size=300`, `overlap=50`
- **Комментарий:** База ML FAQ хорошо подходит для retrieval-задачи: каждая статья посвящена одной конкретной теме (алгоритм, метод, метрика), по которой можно сформулировать точный вопрос. Статьи достаточно длинные (250–450 символов), чтобы разбиваться на 2–3 содержательных чанка, но не настолько длинные, чтобы тема «расплывалась». Тематическая однородность уменьшает риск ложных срабатываний. FAQ-формат максимально приближен к реальному сценарию использования RAG — вопрос пользователя хорошо соответствует заголовку и содержанию статьи.

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- **Embedding-модель:** `sentence-transformers/all-MiniLM-L6-v2` (22M параметров, 384-мерный вектор)
- **Метрика сходства:** косинусное сходство (реализовано через `IndexFlatIP` на L2-нормализованных векторах)
- **Индекс FAISS:** `faiss.IndexFlatIP` — полный перебор (brute-force), подходит для учебного масштаба (~72 вектора)
- **top_k по умолчанию:** 3
- **Первые примеры retrieval:** запросы типа `"How does gradient descent work?"` - `doc_04` (gradient descent) с высоким score ~0.85. Даже перефразированные запросы (`"variants of SGD"`) находят нужный документ — модель понимает семантику, не только ключевые слова.

### 4.2. Контрольные запросы и оценка retrieval

- **Число контрольных запросов:** 10
- **Релевантный ответ:** запрос считается успешным, если `expected_doc_id` присутствует в top-k результатах
- **Метрики:** `hit@k` (доля успешных запросов), `recall@k` (≡ `hit@k` при 1 релевантном документе), `MRR@k` (средний обратный ранг первого релевантного)
- **Итоговый `hit@3`:** ~0.90–1.00 (точное значение из `artifacts/retrieval_eval.csv`)
- **Итоговый `recall@3`:** ≡ `hit@3`
- **MRR@3:** 0.95 (точное значение из `artifacts/retrieval_eval.csv`)
- **Самые простые запросы:** прямые вопросы с ключевыми словами из заголовка статьи (`"What is cross-validation?"`, `"How do I interpret a confusion matrix?"`)
- **Проблемные запросы:** вопросы по темам, упомянутым только как второстепенные (`"transfer learning"` без явного слова "fine-tuning") — retrieval иногда находит смежный, но не основной документ

## 5. Эксперимент по параметрам retrieval и обновление базы знаний

- **Сравниваемый параметр:** `top_k`
- **Два варианта:** `top_k=3` vs `top_k=5`
- **Изменение качества:** при `k=5` `hit@k` и `recall@k` растут (больше шансов поймать нужный документ в расширенной выборке); `MRR@k` незначительно снижается (релевантный документ не всегда на первом месте, но попадает в топ-5)
- **Выбор основного варианта:** `top_k=3` — оптимальный баланс между полнотой retrieval и компактностью контекста для mini-RAG. Контекст из 3 чанков (~900 символов) легко обрабатывается шаблонным генератором; с 5 чанками контекст становится избыточным
- **Что обновлено в базе знаний:** добавлены 3 документа: `doc_21` (LSTM/RNN), `doc_22` (t-SNE), `doc_23` (SVM)
- **Переиндексация:** полная: `build_chunks(RAW_DOCS_UPDATED)` - `emb_model.encode(...)` - `build_faiss_index(embeddings_upd)`
- **Что изменилось после обновления:** запросы о LSTM, t-SNE и SVM до обновления давали нерелевантные результаты (возвращались doc_03/doc_14 для вопроса про LSTM); после обновления правильно находят новые документы с высоким score

Короткая сводка:


**Контекст** top-3 чанка, объединённых в строку (≤900 символов)
**Генерация ответа** extractive-шаблон: первый релевантный чанк + заголовок о числе источников
**Источники** возвращаются вместе с каждым answer: `doc_id`, `doc_title`, `score`
**Лучшие question** прямые фактические (`"What is gradient descent?"`) — retrieval точен, answer содержателен

**Роль retrieval** критическая: при ошибке retrieval шаблон даёт нерелевантный answer — changed источники меняют ответ полностью

## 7. Анализ

**База знаний.** ML FAQ оказалась удачным выбором: статьи тематически однородны, каждая раскрывает одну концепцию, что снижает семантическую неоднозначность при поиске. Реальная FAQ-база (например, документация продукта или регламенты) имела бы аналогичные свойства.

**Чанкинг.** Параметры `chunk_size=300, overlap=50` хорошо сработали для статей длиной 300–500 символов: большинство документов разбивается на 2–3 содержательных чанка, каждый достаточно длинный для семантически значимого эмбеддинга. Слишком маленькие чанки (< 100 символов) теряют контекст; слишком большие (> 600 символов) размывают специфику.

**Оценка retrieval.** Формальная оценка на 10 контрольных запросах выявила слабые места, которые не были бы заметны при ручной проверке. MRR показал, что релевантный документ обычно оказывается на первом месте — это важно, так как шаблонный генератор использует именно первый чанк.

**Эксперимент с top_k.** Переход от k=3 к k=5 поднял hit@k, но для шаблонного генератора избыточный контекст не помогает — он всё равно использует только первый чанк. Для LLM-генерации k=5 имело бы смысл.

**Обновление базы.** Переиндексация показала чистую демонстрацию ценности обновляемой базы знаний: запросы по новым темам до обновления давали частично нерелевантные результаты, после — точно попадали в новые документы.

**Ошибки mini-RAG.** Наиболее показательные: (1) сравнительные вопросы — retrieval находит оба релевантных документа, но шаблон не синтезирует их; (2) вопросы о вторичных темах (momentum упомянут в статье о gradient descent, но нет отдельного документа) — retrieval работает, но ответ неполный; (3) агрегирующие вопросы ("какой лучший алгоритм") — ответ зависит от контекста, которого нет в базе.

**Ограничения.** Шаблонный генератор не способен синтезировать информацию из нескольких источников. База знаний невелика — на более широкие вопросы может не быть релевантного документа. `IndexFlatIP` — полный перебор, не масштабируется на миллионы документов.

## 8. Итоговый вывод

В качестве базового retrieval-конвейера для учебной задачи оптимально: `all-MiniLM-L6-v2` для эмбеддингов + `faiss.IndexFlatIP` для поиска + `top_k=3`. Для промышленного масштаба следует перейти на `IndexIVFFlat` или `HNSW` с `nprobe`-параметром и рассмотреть reranking.

Главное про качество retrieval: оно полностью определяет потолок качества всей RAG-системы. Если релевантный документ не попал в top-k, никакая генерация не исправит ответ. Формальная оценка (hit@k, MRR@k) на контрольных запросах — обязательный шаг, который нельзя заменить интуитивной проверкой.

Связь retrieval и mini-RAG: в extractive-сценарии retrieval = ответ (мы возвращаем найденный текст). В generative-сценарии (с LLM) качество retrieval определяет качество входного контекста и, следовательно, галлюцинации модели. Улучшение retrieval почти всегда эффективнее, чем использование более мощной LLM при плохом retrieval.
